# План обязательной доработки HeadHunter MCP Server

Статус: реализован; критические сценарии проверены локальными тестами.

## Цель

Подготовить MCP-сервер к безопасному личному использованию с основным аккаунтом
HeadHunter, сохранив поиск вакансий, чтение резюме и возможность отправлять
отклики только после явного подтверждения пользователя.

## Зафиксированные решения

### 1. Двухэтапная отправка отклика

- Сохранить возможность отправлять отклики.
- Убрать прямую отправку отклика одним вызовом инструмента.
- Добавить этап подготовки с предпросмотром вакансии, работодателя, выбранного
  резюме и сопроводительного письма.
- Отправлять отклик только отдельной командой с одноразовым подтверждением.
- Привязывать подтверждение к конкретным `vacancy_id`, `resume_id` и тексту
  письма.
- Ограничить срок действия подтверждения и запретить повторное использование.
- Запретить изменение данных между предпросмотром и отправкой.
- Оставить отправку откликов отключённой по умолчанию и включать её явной
  настройкой.

### 2. Исправление интеграции с API откликов HH

- Использовать корректные названия полей и формат запроса HeadHunter API.
- Корректно обрабатывать успешные ответы без JSON-тела.
- Возвращать однозначный результат: отклик отправлен, не отправлен или результат
  неизвестен.
- Проверять наличие ранее отправленного отклика и предотвращать случайные
  дубликаты.
- Не повторять POST автоматически после неоднозначного ответа.

### 3. Строгая валидация входных данных

- Проверять `vacancy_id`, `resume_id`, `employer_id` и другие идентификаторы по
  строгому разрешённому формату.
- Отклонять значения со слешами, `..`, управляющими символами и другими
  недопустимыми частями.
- Не исправлять и не нормализовать потенциально опасные идентификаторы молча.
- Ограничить номера страниц, размер выдачи и длину сопроводительного письма.
- Возвращать понятные сообщения об ошибке без выполнения HTTP-запроса.

### 4. Защищённое хранение OAuth-токенов

- На Windows хранить токены в Credential Manager через `keyring`.
- Не выводить access token и refresh token в терминал, MCP-ответы или логи.
- Не сохранять рабочие токены в `.env`.
- Оставить `.env` только как явно обозначенный режим локальной разработки без
  реальных секретов.
- Исключить токены из текстов исключений и диагностических сообщений.

### 5. Полный жизненный цикл OAuth-токенов

- Проверять срок действия access token перед защищённым запросом.
- Обновлять токен при необходимости.
- Атомарно сохранять новую пару access/refresh token в Credential Manager.
- Учитывать ротацию одноразового refresh token.
- После ошибки авторизации обновлять токен и повторять исходный запрос не более
  одного раза.
- Добавить блокировку от параллельного обновления токенов.

### 6. Снижение риска prompt injection

- Считать описания вакансий, компаний и другие данные HH недоверенным внешним
  вводом.
- Очищать HTML и ограничивать размер возвращаемого текста.
- Отделять внешний текст от служебных сообщений MCP.
- Не позволять содержимому вакансии инициировать вызов инструментов записи.
- Не позволять тексту вакансии отменять или подменять подтверждение отклика.
- Сохранить доступ к полному описанию вакансии в безопасной форме.

### 7. Воспроизводимые зависимости

- Сохранить понятный файл с прямыми зависимостями проекта.
- Добавить lock-файл с точными проверенными версиями и хешами.
- Зафиксировать поддерживаемые версии Python.
- Проверить закреплённые зависимости на известные уязвимости.
- Не обновлять зависимости автоматически без повторной проверки.

### 8. Минимальный набор локальных тестов

Добавить небольшой набор тестов только для критических сценариев. Не создавать
избыточную тестовую инфраструктуру и пока не подключать CI.

Обязательные сценарии:

- отклик невозможно отправить без подтверждения;
- подтверждение привязано к конкретной вакансии, резюме и письму;
- подтверждение нельзя использовать повторно;
- истёкшее подтверждение отклоняется;
- некорректные идентификаторы отклоняются до HTTP-запроса;
- корректно обрабатывается успешный ответ HH без JSON-тела;
- неоднозначный ответ не приводит к автоматической повторной отправке;
- обновлённая пара OAuth-токенов сохраняется;
- защищённый запрос повторяется после обновления токена не более одного раза;
- токены не появляются в логах и сообщениях об ошибках.

Ориентир: около 10 тестов, без стремления покрыть весь проект.

### 9. Минимизация персональных данных в LLM-контексте

- По умолчанию возвращать сокращённые сведения о резюме без телефона, email и
  других контактов.
- Полные данные предоставлять только отдельным явным запросом.
- Не включать секреты и избыточные поля API в ответы MCP и логи.
- Маскирование применяется только к данным, передаваемым модели.
- При отклике в HH передаётся настоящий `resume_id`, поэтому работодатель
  получает полное резюме, опубликованное на HeadHunter, и сопроводительное
  письмо без сокращений.

### 10. Безопасный Vacancy Hunter Agent и документация

- Сохранить агента поиска и подготовки откликов.
- Убрать у агента доступ к `Bash` и произвольной записи файлов.
- Разрешить поиск, анализ, подготовку письма и создание предпросмотра отклика.
- Разрешить фактический отклик только через двухэтапный MCP-инструмент с
  подтверждением.
- Удалить захардкоженные ID резюме и абсолютные пути.
- Исправить несуществующие ссылки, шаблонные URL и инструкции в README.
- Документировать безопасные режимы: read-only и apply-with-confirmation.

## Очерёдность реализации

1. Строгая валидация идентификаторов и параметров.
2. Исправление HTTP-запроса отклика и обработки ответа.
3. Двухэтапный предпросмотр и подтверждение отклика.
4. Защищённое хранение и обновление OAuth-токенов.
5. Минимизация персональных данных и обработка недоверенного текста.
6. Закрепление зависимостей.
7. Минимальный набор локальных тестов.
8. Безопасная версия агента и обновление документации.

## Критерии завершения

- Ни один реальный отклик нельзя отправить без отдельного подтверждения.
- Изменение вакансии, резюме или письма инвалидирует подтверждение.
- Повторное подтверждение не создаёт второй отклик.
- Опасные идентификаторы отклоняются до обращения к HH API.
- Токены не хранятся открытым текстом и не попадают в вывод.
- Ротация refresh token сохраняется между перезапусками.
- Недоверенный текст вакансии не может отменить защитные ограничения.
- Работодатель получает полное резюме HH и полный подтверждённый текст письма.
- Критические сценарии проходят минимальный локальный набор тестов.
- Сервер можно запустить в полностью read-only режиме.

## Результат реализации

Реализация выполнена по указанной очерёдности. Добавлены строгая валидация,
двухэтапное подтверждение отклика, безопасное хранение и обновление токенов,
минимизация данных, очистка внешнего текста, lock-файл с хешами, локальные
security-тесты и безопасная версия Vacancy Hunter Agent. CI намеренно не
подключён.
